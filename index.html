What this is

AI-generated text

A for-loop over the unsolved

The Erdős problem corpus is 1179 questions, collected and maintained at erdosproblems.com. Google DeepMind's formal-conjectures repository had formal Lean statements for 374 of them. This project wrote the remaining 805, completing Milestone 1: all open Erdős problems formalized.

The premise came from doing one by hand. After contributing problem 13, it was clear the remaining few hundred were not a research problem but a loop — given enough tokens to run it.

This work contains no proofs. Every theorem here ends in sorry. The artifact is the statement: a claim rendered in Lean's logic precisely enough that a proof assistant would accept a proof of it. That sounds like the easy half. It is not, and the second pass is what this page is mostly about.

Why stating is hard

A formal statement can compile perfectly and still be the wrong claim. It can be trivially true, so that proving it establishes nothing. It can be trivially false, so that no proof exists. It can quietly assert the opposite of what a problem asks, or answer a question the source resolved years ago in the other direction. Lean checks that a statement is well-formed. Nothing in the toolchain checks that it is faithful — that job has no compiler, and it is the job the second pass does.

First pass

Formalization

Each of the 805 problems went through four agent stages, one at a time:

StageWhat the agent did
FormalizeFetch the problem from erdosproblems.com, write the Lean statement, confirm lake build passes.
StyleConform to the upstream repository's conventions per its AGENTS.md.
ReviewCheck against a 60-point checklist derived from the upstream guidance.
FixApply whatever the review turned up.

The orchestration was deliberately unremarkable — a tmux session on a 2-vCPU cloud box, left running for days:

$ cat todo-conjectures.txt | xargs -I % claude --dangerously-skip-permissions \
    "Read FORMALIZE_CONJECTURE.md. Apply to problem %. 
     Write output to conjectures/%.lean. Ensure `lake build` passes."

Two things governed the schedule, and neither was compute. The weekly token allowance ran out twice. And parallelism turned out to be the wrong instinct: running problems concurrently burned the per-session limit faster without finishing sooner, so the loop went back to one at a time. Concurrency does not lower the bill — it only reaches the ceiling earlier.

Second pass

AI-generated text

Adversarial review

The first-pass corpus is a draft. The second pass sends a stronger model at each problem with a different brief: assume the formalization is wrong and find out how.

The unit of work

One problem, one agent, one commit. The agent recovers the original problem page from an archived capture rather than working from memory, re-derives the mathematics independently, audits the first-pass review claim by claim, and writes at most two files: a corrected conjectures-v2/N.lean and a review note at fable-review/N.md. The first-pass file is immutable input — a reviewer may not edit its own evidence.

What gets checked

Part A · Semantic fidelity

Statement fidelity against the recovered source. Lean semantics traps. Definitional correctness. Question form and answer polarity. Solution status as of today, not as of the capture.

Part B · Scholarship

Citation keys resolve; bibliographic data is recovered, never invented. Variants named on the source page are present.

Part C · Craftsmanship

Readability, docstrings that match the code beneath them, reuse of Mathlib rather than reinvention.

Part D · Mechanical checks

Greps for sorry outside proof bodies, fragile tactics, binder placement, missing docstrings.

Part E · Prior-review audit

Every claim the first-pass reviewer made, re-derived from scratch.

Two standing rules

Never fabricate a citation. Where a journal, volume, or page number could not be recovered from a real source, the entry says so and stops. A plausible-looking reference is worse than an admitted gap, because it survives review.

Recover the source; don't recall it. A model's memory of a famous problem is exactly where a subtle misstatement comes from. Every review in the most recent batch worked from an archived page capture, with the problem's status cross-checked against an independent metadata mirror — because status drifts, and captures go stale.

The defect taxonomy

The interesting failures are the ones a compiler cannot see. They fall into three families.

Polarity. The Lean asserts the direction the source refutes, or drops the answer(False) wrapper on a problem that has been disproved. The statement looks impeccable and says something false. This is the most dangerous class precisely because it is the most well-formed.

Vacuity and degeneracy. The statement is provable, or refutable, for reasons unrelated to the mathematics. The mechanisms recur: Mathlib's junk values at degenerate inputs (Real.log 0 = 0, sInf ∅ = 0, rpow 0 0 = 1, φ(0) = 0); a default binder left unconstrained so a caller can instantiate a definition outside its intended domain; a constant quantified inside the parameter it was supposed to be independent of, letting it absorb the very factor the problem is about; a bound that is simply false at small n because log log n is negative there.

Bibliography. Citation keys used but never defined, references with no data behind them, and bounds attributed to the wrong paper.

Case files

AI-generated text

Four that earned their keep

Aggregate counts undersell what these reviews actually do. Four representative catches:

90A conjecture asserted three months after it was disproved

The unit distance problem — a $500 Erdős prize — was disproved in May 2026, following a construction found by a machine. The archived page capture predates that and still shows the OPEN banner; the formalization asserted the conjecture positively.

Catching it required distrusting the capture and checking an independent status mirror. But the second half is the more instructive part: naively negating the statement would have produced a "disproof" that is trivially satisfiable by a two-point witness, since the bound is already false there for unrelated reasons. The corrected file carries a small-cardinality guard so that the negation actually says what the disproof says.

56A helper definition right by count, wrong by elements

A supporting definition produced sets of the correct size containing the wrong members. Every reading of the code agreed it was fine; the counts checked out. Only brute-force enumeration of small cases settled it.

That technique — stop reading the definition, run it on n = 3, 4, 5 and look at what comes out — became standard for the rest of the corpus and has since caught defects in eight further problems.

55A constant on the wrong side of a quantifier

The statement bound its constant inside the universally quantified parameter, so the constant was free to depend on it — and could absorb exactly the growth factor the problem asks about. Perfectly well-typed, entirely provable, and mathematically empty.

Quantifier order is where formalization fidelity most often dies quietly, because both orderings compile and both read fluently in English.

86The review that was wrong, and how that surfaced

A review found that loopless := ⟨fun …⟩ failed to compile against a graph structure's field, citing archived build transcripts as evidence, and the fix was propagated to three other files. It was backwards. Current Mathlib defines that field as a structure, so the constructor is required; the transcripts dated from before the change and described an environment that no longer existed.

The build caught it — lake build went red, and a follow-up commit reverted all four files. Worth recording rather than quietly deleting: evidence recovered from a log dates a claim about the environment, and generalizing one such claim across a corpus is how a single bad inference reaches four files at once.

Auditing the auditor

AI-generated text

The first-pass reviews were themselves unreliable

Part E of every second-pass review re-derives the claims made by the first-pass reviewer. That audit found failure modes worth naming, because they are what automated review looks like when it goes wrong:

  • Fabricated verification. Citations certified as "matching the source" that the source does not contain — a journal and volume asserted for what is only an arXiv preprint; a prize described as awarded where the page says only that the problem was proved.
  • Right conclusion, unsound argument. A restriction correctly kept, justified by reasoning that is false for even exponents. The verdict passes; the reasoning would not survive a reader.
  • Unsound "critical fixes." A proposed correction that would have introduced a misformalization into a statement that was already right.
  • Fixes that never landed. Defects correctly identified, then applied only to a styled copy of the file — never to the artifact under review.

The lesson generalizes past this project: a review pass that produces confident prose is not evidence of a review that happened. What makes the second pass checkable is that every claim in it points at a recovered source a reader can open.

Does model strength show up in the numbers?

Problems 1101–1179 were reviewed twice, independently, by two models of different capability — the second run blind to the first. The verdict distributions look almost inverted:

ReviewerAcceptAccept w/ nitsNeeds revisionSources recovered
Stronger model0522779 / 79
Cheaper model16214233 / 79
 Same 79 problems, same instructions, independent runs.

The cheaper model flags more revisions — but mostly convention-level ones: recasting statements into a preferred answer form, in a few cases via shims that would not compile or an import that does not exist upstream. It also recovered the original source for fewer than half the problems, and endorsed fabricated references in at least four. Where it did land real mathematical catches, those catches were largely a subset of the stronger model's.

The practical read is not "cheap models don't work." It is that the two tiers fail differently, which suggests splitting the work: let a cheap tier do source recovery, docstrings, and citation keying, and reserve the expensive tier for polarity, vacuity, and quantifier order — the defects that need someone to actually do the mathematics.

Verification

AI-generated text

It builds

The corrected corpus compiles in this repository — lake build ErdosV2, 3057 jobs, no external checkout — with only the expected declaration uses 'sorry' warnings. That is the honest bar: the statements are well-formed Lean, and nothing claims to be proved.

The most recent build broke on 7 of 202 files, and all seven were environment drift rather than formalization defects: a graph structure's field became a structure, a Mathlib module became a deprecated shim, two files needed imports for constants that had moved, and one binder needed an explicit type where inference had silently changed. Worth noting that this is the ordinary weather of building against a fast-moving library — and worth noting that all seven were caught by the compiler, unlike everything else on this page.

What is not verified

Reviews are written without a compiler in the loop; they are checked against the build afterward, on a separate machine. Bibliographic entries marked deferred remain unresolved rather than guessed. And there is no human review gate here at all — unlike the upstream DeepMind project, which has one. The quality bar is the second pass.

A benchmark that ages well

909 problems have not had a second pass yet. The plan is to finish them, then re-run the whole corpus as new models ship.

That re-run is the point. Formalization fidelity is an unusually clean thing to measure: the mathematics is fixed and public, the claim is already known, and the only question is whether a model can restate it in Lean without changing what it means. There is no reward-hackable score — a statement is faithful or it isn't, and a reader with the source page can check. As models improve, the defect counts on this page should fall, and the classes that survive longest are the ones worth knowing about.

Cost, for anyone considering the same: second-pass reviews run roughly 106k–144k tokens each, putting a hundred-problem batch near 12M. The weekly allowance has been the binding constraint at every stage of this project — not compute, not the model, not the mathematics.
