## Summary

The problem (DISPROVED, proof verified in Lean): *"Let $A\subset\mathbb{N}$ be
infinite. Must there exist some $k\geq 1$ such that almost all integers have a
divisor of the form $a+k$ for some $a\in A$?"* — equivalently, must some
translate $A+k$ be a Behrend sequence? The answer is **no**: Davenport–Erdős
[DaEr51] showed every Behrend sequence has divergent reciprocal sum, so any
infinite $A$ with $\sum 1/a<\infty$ is a counterexample; Ruzsa gave an
explicit congruence construction, and van Doorn modified it to a
counterexample with $\sum 1/a=\infty$ (the thick version now disproved in
Lean). The Lean theorem (`conjectures/26.lean:52-55`) asserts
`¬ (∀ A : Set ℕ, A.Infinite → ∃ k, 0 < k ∧ IsBehrendSeq (SetTranslate A k))`,
where `IsBehrendSeq B` says the set of naturals with a divisor in `B` has
natural density 1 (encoded as an eventually-≥-(1−ε)N count over
`Finset.range N`). Read back independently, this is exactly the negation of
the question's universal statement — the true direction for a disproved
yes/no question under this pipeline's direct-assertion convention. I found no
semantic defects; the nits are scholarship-level (no bibliography for the
three page keys, no record of the Lean-verified status, the page's three
confirmed variant statements absent) plus one docstring indexing inaccuracy.

## A. Semantic fidelity

**A1. Statement fidelity — pass (source-verified).**

- Recovered verbatim source statement (see Addendum) matches the theorem
  docstring's English (lines 42-43) word for word in substance.
- Independent back-translation of lines 52-55: "it is not the case that for
  every infinite set A of naturals there is a positive k such that the set of
  naturals having a divisor of the form a+k (a ∈ A) has natural density 1."
  This is precisely "the answer to the question is no".
- **Density encoding, verified by hand:** `HasDensityOne S` (lines 14-17)
  says: ∀ε>0, eventually `|S ∩ {0,…,N−1}| ≥ (1−ε)·N` (count cast to ℝ).
  Since the count is trivially ≤ N, this lower-liminf form is exactly
  "density → 1"; no upper bound clause is needed. Not vacuous: satisfied by
  `S = univ` (count = N), violated by e.g. the evens — the notion genuinely
  discriminates.
- **"Almost all" reading:** the page itself equates the question with "$A+k$
  is a Behrend sequence" and defines Behrend via "almost all integers have a
  divisor in $A$" — the density-1 reading, exactly what `IsBehrendSeq`
  encodes. `HasDivisorIn B = {n | ∃ b ∈ B, b ∣ n}` is the set of multiples
  of B, term-for-term the page's "have a divisor of the form a+k".
- **Domain subtlety (0 ∈ ℕ), checked and harmless:** Lean's `Set ℕ` admits
  infinite A containing 0, and `SetTranslate A 1` would then contain 1,
  making the translate trivially Behrend (everything divides by 1). Since
  the theorem is the *negation* of a universal, this only affects whether a
  counterexample containing 0 could be "cheaper" than the source's 1-based
  counterexamples — it cannot: removing 0 from any counterexample A leaves an
  infinite counterexample (translates shrink, `IsBehrendSeq` is monotone
  under ⊆ through `HasDivisorIn`), so the Lean statement is equivalent to
  the 1-based reading. Documented in v2, no defect.
- Not vacuous/trivially true: the statement is true for a genuine
  mathematical reason with an explicit witness — A = {2,4,8,…} = powers of 2:
  for every k ≥ 1 the multiples of {2^i + k : i ≥ 1} have upper density
  ≤ ∑_{i≥1} 1/(2^i+1) ≈ 0.764 < 1, so no translate is Behrend. Nothing in
  the encoding makes it true degenerately (e.g. `HasDensityOne` is
  satisfiable and `IsBehrendSeq (SetTranslate Set.univ 1)` holds, so neither
  side of the implication chain is broken).
- Types: everything in ℕ with the count and (1−ε)·N compared in ℝ after
  casts — arithmetic happens in the intended type; no coercion placed so as
  to truncate.

**A2. Lean semantics traps — pass.**

- **ℕ subtraction:** none (the only subtraction, `1 - ε`, is in ℝ).
- **Division:** none in the code (the docstring's `/N` is prose only).
- **`Finset.range N` off-by-one:** the code counts `{0,…,N−1}` while the

  correct "for all sufficiently large N" unfolding; combined with count ≤ N

  irrelevant). `b = 0` divides only 0 — harmless.
