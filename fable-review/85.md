## Summary

The problem (verbatim from the recovered page): "Let $n\geq 4$ and $f(n)$ be minimal
such that every graph on $n$ vertices with minimal degree $\geq f(n)$ contains a
$C_4$. Is it true that, for all large $n$, $f(n+1)\geq f(n)$?" Status OPEN,
FALSIFIABLE. The Lean file defines `SimpleGraph.ContainsCycle4` (four distinct
vertices in cyclic adjacency), `ForcesCycle4 n d` (every graph on `Fin n` with all
degrees ≥ d contains a C₄), and `minDegreeForCycle4 n = sInf {d | ForcesCycle4 n d}`,
then asserts `∃ N, ∀ n ≥ N, minDegreeForCycle4 (n+1) ≥ minDegreeForCycle4 n`
(`conjectures/85.lean:39-42`). Read back independently: "eventually, f(n+1) ≥ f(n)" —
exactly the affirmative side of the question asked, with `f` a faithful rendering of
the page's `f` (verified term-by-term and on small cases, f(4) = 2 matching the page).
The right-hand side of the upstream formal-conjectures statement
(`answer(sorry) ↔ ∀ᶠ n in atTop, f n ≤ f (n + 1)`) is the same proposition. I found no
semantic defects; only polish-level findings.

## A. Semantic fidelity

**A1. Statement fidelity — pass (source-verified).**

- Back-translation of lines 39-42: "there is an N such that for every n ≥ N, the
  minimal degree threshold forcing a C₄ on n+1 vertices is at least the one on n
  vertices." This is precisely "for all large n, f(n+1) ≥ f(n)", the question as
  asked. `≥` direction checked against the docstring and source: matches (no
  swapped-inequality issue).
- `ForcesCycle4 n d` (lines 18-20): "every graph on n vertices with minimum degree
  ≥ d contains a C₄" — `∀ v, d ≤ G.degree v` is exactly "minimal degree ≥ d" (for
  n ≥ 1 it is equivalent to `G.minDegree ≥ d`; at n = 0 see A2). The set
  `{d | ForcesCycle4 n d}` is **upward closed** (min degree ≥ d+1 implies ≥ d), so
  `sInf` is its least element — exactly the source's "minimal such that", not a
  spurious infimum. It is **nonempty for n ≥ 1**: d = n forces vacuously, since no
  simple graph on n vertices has a vertex of degree n. So `sInf` is well-behaved and
  the "extremal value pinned" concern (problem-36 class) does not arise.
- Small-case hand-verification of the helper defs (batch checklist item; computed
  from the Lean definitions, not the docstring): f(0) = 0 (empty index set, `Nat.sInf
  ∅ = 0`), f(1) = 1, f(2) = 2, f(3) = 3 (vacuous forcing at the first impossible
  degree), **f(4) = 2** — lower bound: two disjoint edges have min degree 1 and no
  C₄; upper bound: a 4-vertex graph with δ ≥ 2 has ≥ 4 edges and every such graph
  (C₄, diamond, K₄) contains a C₄. This **matches the page's "it is easy to check
  that f(4) = 2"**. Also f(5) = 3 (C₅ shows δ = 2 insufficient; K₅ minus a matching
  always contains a C₄). Note f(3) = 3 > f(4) = 2: monotonicity genuinely fails at
  small n, so the `∃ N` ("for all large n") is doing real work and the source's
  "Let n ≥ 4" needs no separate hypothesis — the asymptotic form absorbs it.
- The source's 1-indexed n is the same n here (no sequence indexing to reconcile);
  vertices are `Fin n`, the standard n-vertex model.
- Not vacuous / not trivial: the statement is equivalent to eventual monotonicity of
  the genuine Ramsey-theoretic f (an open problem); no degenerate witness satisfies
  it trivially, and the n < 4 degeneracies are absorbed by `∃ N`.

**A2. Lean semantics traps — pass.**

- No ℕ subtraction, no division, no `Finset.range` anywhere in the file.
- Vacuous quantifiers: two live sites, both benign and both matching the source's
  reading. (i) For d > max possible degree, the hypothesis `∀ v, d ≤ G.degree v` is
  unsatisfiable and `ForcesCycle4 n d` holds vacuously — this is what makes the
  `sInf` set nonempty, and it agrees with the informal convention (a threshold no
  graph attains forces trivially). (ii) At n = 0, `∀ v : Fin 0, …` is vacuously true
  while `ContainsCycle4` is false, so `ForcesCycle4 0 d` is false for every d and
  f(0) = `Nat.sInf ∅` = 0 — a junk value at a parameter the theorem never depends on
  (the `∃ N` statement is insensitive to any finite prefix). Checked explicitly per
  the degenerate-input warning (problems 20/78/80): the smallest quantified
  parameter here is N itself, and no small-n boundary can falsify or trivialize the
  statement.
- "For all large n" is encoded as `∃ N, ∀ n, N ≤ n → …` — the standard, correct
  unfolding of `∀ᶠ n in atTop` (which is literally what upstream uses). Quantifier
  order `∃ N` before `∀ n` is right; nothing for N to absorb (problem-55 class n/a).
- No `liminf`/`limsup`, no real-valued `sSup`/`sInf` junk (problem-33 class n/a):
  the `sInf` here is `Nat.sInf` on a set shown nonempty for all n ≥ 1.
- Strictness: `≥` (non-strict) matches the source's `\geq` at both occurrences
  (min-degree hypothesis and the monotonicity conclusion).
- Instance binder: `∀ (G : SimpleGraph (Fin n)) [DecidableRel G.Adj], …` quantifies
  over (graph, instance) pairs. This is semantically harmless: every `G` has a
  decidability instance classically, and `G.degree` (a `Finset.card`) is independent
  of which instance is supplied, so the proposition is equivalent to the intended
  `∀ G, …`. (The pipeline log shows this binder was added precisely to satisfy the
  `Fintype (G.neighborSet v)` instance — see Addendum.)

**A3. Definitions — pass.**

- `ForcesCycle4` and `minDegreeForCycle4` match their docstrings and the source

- No `sorry` in any `def` (the file's single `sorry` is the theorem proof body,

**C2. Reuse — two flags (static judgment only; not applied).**

- Mathlib has `SimpleGraph.cycleGraph 4` and copy-containment `⊑`
  (`SimpleGraph.IsContained`, `Mathlib.Combinatorics.SimpleGraph.Copy`) — upstream
  states containment as `(cycleGraph 4) ⊑ G`. Equivalent to `ContainsCycle4`; the
  swap would need a new import and is compile-dependent — flagged only.
- Mathlib has `SimpleGraph.minDegree` (in the already-imported
  `SimpleGraph.Finite`); `∀ v, d ≤ G.degree v` is equivalent for n ≥ 1 and avoids
  `minDegree`'s junk value 0 on the empty vertex type (where the explicit ∀ is
  vacuously true instead — a *different* junk convention; see A2). The explicit form
  is arguably the safer of the two; no change recommended.
- **Import-graph note (problem-65-class check, resolved *against* flagging):**
  `sInf` on ℕ requires the `InfSet ℕ` instance, which lives only in
  `Mathlib.Data.Nat.Lattice` — and that module is *not* obviously near any of the
  three imports. Walking the pinned Mathlib (commit 8f9d9cff, the repo's
  `lake-manifest.json` pin; sparse checkout completed via `git show` fallback) shows
  it **is** reachable: `SimpleGraph.DegreeSum` → `Data.ZMod.Basic` →
  `GroupTheory.OrderOfElement` → `Dynamics.PeriodicPts.Lemmas` →
  `Data.Nat.Lattice` (1514-module closure). So the seemingly-unused `DegreeSum`
  import is actually **load-bearing** for `sInf` and must not be "cleaned up".
  Corroborated empirically: the original pipeline log shows this exact file
  compiling (Addendum). A defensive explicit `import Mathlib.Data.Nat.Lattice`
  would be more robust against Mathlib refactors but is a compile-affecting change —
  deferred, noted only.
