## Summary

The problem (OPEN on the source page): call A ⊆ ℕ an *essential component*
if d_s(A+B) > d_s(B) for every B ⊆ ℕ with 0 < d_s(B) < 1, where d_s is the
Schnirelmann density; is B = {2^m 3^n : m, n ≥ 0} an essential component?
Ruzsa ([Ru99]): "The simplest set with a chance to be an essential component
is the collection of numbers in the form 2^m 3^n and Erdős often asked
whether it is an essential component or not; I do not even have a plausible
guess." The Lean file (`conjectures/1146.lean`) defines the Schnirelmann
density as an infimum over ℕ+ (correct), the strict sumset
{n | ∃ a ∈ A, ∃ b ∈ B, n = a + b}, the essential-component predicate over
that strict sumset, and the 3-smooth numbers, then directly asserts
`IsEssentialComponent1146 smoothNumbers23` (line 47) — the corpus's standard
direct-assertion form for an open yes/no question. The definitions
individually match their docstrings and the page's *literal* wording, but the
literal wording presupposes the classical convention that Schnirelmann sums
adjoin 0 (Halberstam–Roth); without it the formal statement is refutable by a
two-line argument, so the artifact does not encode the intended open
question. This is the sole Part A defect; everything else is scholarship
(undefined citation key, truncated quotation) and polish.

## A. Semantic fidelity

**A1. Statement fidelity — DEFECT (statement trivially false as written).**

- Recovered verbatim source statement (see Addendum): "We say that
  $A\subset \mathbb{N}$ is an essential component if $d_s(A+B)>d_s(B)$ for
  every $B\subset \mathbb{N}$ with $0<d_s(B)<1$ where $d_s$ is the
  Schnirelmann density. Is $B=\{2^m3^n : m,n\geq 0\}$ an essential
  component?"
- Independent back-translation of lines 26–48: "for every B ⊆ ℕ with
  0 < d_s(B) < 1, the strict sumset {a + b : a ∈ smooth, b ∈ B} has
  Schnirelmann density strictly greater than that of B." Sentence-by-sentence
  this mirrors the page's letter — but not its meaning, because of the sumset
  convention:
- **[defect] The statement is provably false as written.** Take
  B₀ = ℕ \ {0, 2}. Then d_s(B₀) = 1/2: the defining terms are
  |B₀ ∩ {1,…,n}|/n = 1, 1/2, 2/3, 3/4, … (n = 1, 2, 3, 4, …), whose infimum
  is 1/2, so 0 < d_s(B₀) < 1 holds. Every a ∈ smoothNumbers23 satisfies
  a = 2^m 3^n ≥ 1 and every b ∈ B₀ satisfies b ≥ 1, so every element of
  `sumset1146 smoothNumbers23 B₀` is ≥ 2; hence 1 is not in the sumset, the
  n = 1 term of the density infimum is 0, and
  d_s(sumset) = 0 ≯ 1/2. So `IsEssentialComponent1146 smoothNumbers23` is
  **false**, with an easy proof — and the same argument kills *every* A with
  0 ∉ A, since nothing in `0 < d_s(B)` forces 0 ∈ B (density is computed on
  {1,…,n}). Under this encoding no subset of {1, 2, 3, …} is an essential
  component at all, which contradicts the entire classical theory (Khinchin:
  the squares including 0² are an essential component; Erdős: every basis
  is; Ruzsa's [Ru87] characterization behind Problem #37 presupposes
  essential components exist). The intended reading — standard in the
  Schnirelmann literature (Halberstam–Roth, *Sequences*), used by the
  classical examples (which all contain 0), and matched by the sibling
  `conjectures/35.lean`, which explicitly hypothesizes 0 ∈ B for the related
  Erdős density inequality — is that the Schnirelmann sum adjoins 0:
  C = (A ∪ {0}) + (B ∪ {0}) = A ∪ B ∪ (A+B) ∪ {0}. Then C ⊇ B, so
  d_s(C) ≥ d_s(B) automatically, and the question is precisely whether
  adding the 3-smooth numbers gives a *strict* increase — a genuine open
  question. Fixed in v2 via a new `schnirelmannSum1146` def, with the
  counterexample documented (Addendum fix 1). The archived styled copy
  (`deepmind/deepmind/1146.lean`) and the upstream formal-conjectures file
  (recovered from the logs) share the same strict-sumset flaw — the upstream
  in question form `answer(sorry) ↔ …`, where it silently makes the answer a
  trivial "False" rather than asserting a falsehood.
- Quantifier structure otherwise matches (∀ B inside the predicate; A
  instantiated to the smooth numbers); types are appropriate (ℝ-valued
  density, `Set ℕ` throughout, casts placed so arithmetic is real).
- Indexing: the density's inf_{n ≥ 1} is realized by `n : ℕ+` and
  `Finset.Icc 1 n` = {1,…,n} — term-by-term exact against the source's
  d_s(A) = inf |A ∩ [1, n]|/n; membership of 0 in a set is correctly
  invisible to its density.

**A2. Lean semantics traps — pass except as absorbed into A1.**

- No ℕ subtraction anywhere.
- Division: only real division, by `(n : ℝ)` with n : ℕ+ ≥ 1 — never zero.
- `Finset.Icc 1 n` (not `range`) — no off-by-one; matches {1,…,n} exactly.
- `⨅ n : ℕ+, …` in ℝ: the value family is nonempty and bounded below by 0
  (each term is a nonnegative count divided by a positive real), so the
  conditionally-complete-lattice infimum is genuine (no sInf-junk), with
  value in [0, 1].
- No vacuous bounded quantifiers; no filter/limsup encodings; strict
  inequalities (0 < d, d < 1, >) match the source's strict inequalities.
- `Finset.filter (· ∈ A)` needs `DecidablePred`; `open Classical` (line 5)
  supplies it, and the originating log records the build succeeding.
- The degenerate-witness check is where the file fails — see A1.

**A3. Definitions — pass individually; the composition is the defect.**

- `schnirelmannDensity1146` (line 13) matches its docstring and the standard

  the strict sumset it claims to be). `smoothNumbers23` (line 33) is exactly
  {2^m 3^n} — contains 1 (m = n = 0), never 0. No `sorry` in any def.
- The drift is between `IsEssentialComponent1146` and the *intended*
  essential-component notion, per A1: the def computes what it says, but

**A4. Question form and answer polarity — form pass (corpus convention);

## E. Prior-review audit (`deepmind/ai-review/1146.md`)

The prior review (written against the styled copy, which still had the
`sumset` def later replaced upstream by pointwise `A + B`) is accurate on
surface facts but fails on exactly the classes this pipeline exists to catch:

1. **It endorsed the fatal encoding while describing its mechanism.** Its §5
   states: "`smoothNumbers23` does not contain 0 … This means summing with
   `smoothNumbers23` always shifts elements by at least 1, which is
   important for the density analysis. The formalization correctly captures
   this." The shift-by-≥-1 is precisely what forces 1 ∉ A + B (for B ∌ 0)
   and hence d_s(A + B) = 0 — the trivial refutation of A1. The review
   walked up to the defect, articulated it, and blessed it — the same
   pattern as the 1005 audit (endorsing an encoding that contradicts its own
   reading of the source).
2. **Its verdict is wrong.** §6: "No mathematical flaws identified. The
   formalization is complete and correct." False — the encoded proposition
   is provably false while the problem is open.
3. **Half-finished degenerate-case analysis.** §6's "one potential concern"
   correctly derives that 0 < d_s(B) forces 1 ∈ B (n = 1 term) and calls the
   handling correct — but never runs the same n = 1 test on the *sumset*
   side, which is where it fails.
4. **False Mathlib claim.** §1: "No existing Mathlib or project utility
   captures Schnirelmann density, so the local definition is justified."
   Mathlib has had `schnirelmannDensity` (`Mathlib.Combinatorics.Schnirelmann`)
   since well before the pinned v4.28.0, where its presence was verified
   directly (C2). Same class as the 1002 audit's wrong-Mathlib-semantics
   finding.
5. **Self-contradictory smooth-numbers claim.** §1 asserts
   "`smoothNumbers23` also includes 0 (via m = 0, n = 0 giving k = 1, …)" —
   m = n = 0 gives k = 1, not 0, and its own §5 says the opposite
   (correctly). The hedge that `Nat.smoothNumbers 4` is only "semantically
   equivalent for n ≥ 1" is confused: the two sets are extensionally
   *equal* (both exclude 0, both contain 1).
6. **Citation instincts half-right, unfollowed.** §2 correctly suspects
   [Va99] "likely refers to the volume … rather than Ruzsa as author", but
   guesses "Varia", never identifies the site's actual key (the 1999
   Budapest booklet), and does not flag the styled copy's fabricated
   bibliographic data for [Va99] (a 2009-published survey dated 1999) — nor
   the truncated, unattributed Ruzsa quotation.
7. **What it got right:** the sumset-duplicates-pointwise-`Set.add`
   observation (adopted upstream per the recovered diff); the cross-file
   reuse survey (35/37/1146 sharing definitions — verified against
   `conjectures/35.lean` and `conjectures/37.lean` in this repo); the
   `answer(sorry)` shape call for the styled copy; the 1 ∈ B derivation in
   item 3 above, as far as it went.
